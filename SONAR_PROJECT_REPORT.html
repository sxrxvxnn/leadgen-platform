Origin & Problem Statement

Sonar was built to solve a problem every early-stage B2B founder faces: finding the right companies and people to reach out to is painfully manual. Existing tools like Apollo, ZoomInfo, and Hunter are either too expensive, too generic, or require hours of manual list-building and copy-pasting before a single email can go out.

The project started as a simple lead scraper — a script that pulled developer profiles from GitHub and HackerNews hiring threads. Over time it evolved into a full intelligence platform with three distinct features, each solving a different part of the outreach problem:

Problem 1 — Finding Companies
No easy way to discover, enrich, and monitor target companies without paying $500+/mo for enterprise tools.
Problem 2 — Finding People
Even after finding a company, identifying the right decision-makers and getting verified contact details requires multiple tools.
Problem 3 — Reaching Out
Generic outreach has <1% reply rates. Personalised messages require hours of research per lead.
02

How It Evolved

Phase 1 — Foundation
GitHub + HN Scraper → Contacts Database
The first version was two Python scripts: one that crawled GitHub user profiles by searching for developers with certain follower counts and tech stacks, and one that parsed monthly "Ask HN: Who is hiring?" threads. Both dumped data into a Supabase sonar_contacts table. No UI existed yet.
Phase 2 — API Layer
FastAPI Backend + Supabase Auth
The scrapers were wrapped into a FastAPI application with user authentication via Supabase Auth. Basic CRUD endpoints were built for leads and companies. Row Level Security enforced per-user data isolation from day one — every table is user_id-scoped.
Phase 3 — React Dashboard
Companies, Leads, Prospect Pages
A React 19 single-page app was built in JSX (no TypeScript). Three core pages emerged: Companies (target account tracking), Leads (contact management), and Prospect (AI-powered discovery via PDL). Inline styles were used throughout — no Tailwind — for fine-grained control.
Phase 4 — AI Enrichment
Groq LLM + Multi-Source Intelligence
Groq (llama-3.3-70b-versatile) was integrated as the primary LLM. Company auto-fill started pulling data from LinkedIn scraping. Similar-companies discovery was built using G2, Capterra, and Crunchbase search snippets fed to a single Groq call. ICP scoring was added to rank prospects automatically.
Phase 5 — Buying Signals
Real-Evidence Signal Detection
The buying signals system was built and then completely overhauled: 8 targeted web searches (hiring, funding, partnerships, product launches, leadership changes) + GitHub org API + HN Algolia search → evidence-only Groq prompt. Signals only appear if there is a real source URL to back them up.
Phase 6 — Email Sequences + Tracking
Automated Outreach with Full Observability
Multi-step email sequences with per-lead enrolment, warmup scheduling, reply detection, and self-hosted tracking pixels. A 1×1 pixel endpoint records every open; a redirect endpoint records clicks. All stored in Supabase email_events.
Phase 7 — Security Hardening
SSRF Protection, Prompt Security, Audit Logging
A full security layer was added: SSRF blocking for all user-supplied URLs, prompt injection detection for LLM calls that process scraped web content, UUID validation, structured JSON audit logs for every auth event, and per-path rate limiting.
Phase 8 — Current
Production on Vercel Fluid Compute
Both frontend (Sonar dashboard) and backend (FastAPI ASGI) run on Vercel Fluid Compute. Seven cron jobs run daily/weekly for data collection, sequence processing, and contact enrichment. PostHog tracks product usage and Sentry captures runtime errors.

System Architecture

The platform is split into three layers: a React SPA served from Vercel's CDN, a FastAPI backend running on Vercel Fluid Compute (serverless Python), and a Supabase PostgreSQL database with Row Level Security. All communication between layers uses HTTPS with JWT authentication.

Database Schema

Every table is scoped by user_id with Supabase RLS policies. The backend uses the service-role key (bypasses RLS) while the frontend anon key respects the policies. All id fields are UUIDs validated by security.py before use.

External Integrations

🤖
Groq — Primary LLM
llama-3.3-70b-versatile for all reasoning tasks (similar companies, buying signals, ICP scoring, DM generation). llama-3.1-8b-instant for fast classification. Fallback to Gemini 2.0 Flash when Groq is unavailable. All calls tracked in PostHog.
🔍
Brave Search — Web Intelligence
2,000 free queries/month. Used for buying signals (8 searches per company), similar companies from G2/Capterra/Crunchbase, LinkedIn URL discovery, and website finding. DuckDuckGo DDGS is the fallback when Brave credits are exhausted.
👤
PDL (People Data Labs)
SQL-mode prospect search. $0.05–0.10/new match. Scroll-token pagination for large result sets. Powers the Discovery/Prospects feature — the only paid-per-result API in the platform.
📧
Hunter.io + Apollo.io
Email finding pipeline. Hunter first (25 free/month, $49/mo upgrade). Apollo fallback (50 free/month). Both also used for email pattern detection — once a domain's format is known, emails are generated for free without hitting the API again.
🏢
ProxyCurl
Deep LinkedIn enrichment at $0.01/call. Used when a lead has a known LinkedIn URL. Returns work email, phone, full profile, current company, and job history. Not hit until cheaper methods are exhausted.
🗺️
Google Maps + GitHub + HN Algolia
Google Maps geocodes company HQ addresses for the globe view ($0 within $200 monthly credit). GitHub REST API finds company repos and recent activity (free). HN Algolia searches for company mentions in Hacker News stories (free).
🕷️
Firecrawl
Website scraping for company auto-fill when direct HTTP scraping fails. Used selectively — most website content is fetched directly via requests + BeautifulSoup to preserve Firecrawl credits for hard-to-scrape sites.
📊
PostHog + Sentry
PostHog tracks product events (features used, LLM token consumption) via OTLP log shipping from the backend. Sentry captures runtime exceptions with 10% trace sampling and 5% profiling.

Security Model

Security is enforced at multiple layers — network, application, AI, and database — rather than relying on any single control.

Security Layers
Layer 1 — Network
Rate Limiting + SSRF Blocking
SlowAPI per-IP limits + custom path limits for auth/enrich endpoints. All user-supplied URLs checked against private IP ranges before HTTP requests are made.
Layer 2 — Application
JWT Auth + UUID Validation + Input Sanitisation
Every protected endpoint validates the Supabase JWT. All row IDs are regex-validated as canonical UUIDs. Pydantic models enforce types and constraints at the API boundary.
Layer 3 — AI Safety
Prompt Injection Detection + Output Validation
All scraped web content is sanitised through prompt_security.py before entering an LLM prompt. Unicode homoglyphs are normalised. AI output is validated against an allowed-keys schema.
Layer 4 — Database
Row Level Security (RLS)
Supabase RLS policies enforce that every SELECT/INSERT/UPDATE/DELETE is scoped to the authenticated user's user_id. The backend uses the service-role key which bypasses RLS — but that key never leaves the server.
Layer 5 — Audit
Structured JSON Audit Logs
Every auth event (login success/failure, signup, password reset) and bulk operation emits a structured JSON log line with timestamp, user_id, IP, and event type. Shipped to PostHog via OTLP.

Automated Jobs (Cron)

Seven scheduled jobs run automatically via Vercel Cron. All are authenticated with a shared CRON_SECRET header so they cannot be triggered externally.

ScheduleEndpointWhat It Does
Daily 08:00 UTC/api/sequences/warmup-cronGradually increases email sending volume to warm up the sending domain and avoid spam filters.
Daily 09:00 UTC/api/sequences/process-cronSends all queued sequence emails for the day based on each enrolment's next_send_at.
Daily 10:00 UTC/api/sequences/check-repliesChecks for email replies and marks enrolments as replied/paused to stop the sequence automatically.
Daily 02:00 UTC/api/cron/scrape-githubRotates through 14 GitHub search queries to add new developer profiles to sonar_contacts.
Daily 04:00 UTC/api/cron/enrich-contactsEnriches newly scraped contacts with email/phone data using the Hunter → Apollo pipeline.
Weekly Mon 03:00/api/cron/scrape-hnScrapes the latest "Ask HN: Who is hiring?" thread and extracts company and contact data.
Weekly Sun 05:00/api/cron/refresh-contactsRefreshes stale contact records that haven't been updated in 30+ days.
